## How to use this prompt

Act as a senior Three.js/WebGL engineer, scientific-visualization engineer, anatomy educator, realtime-data engineer, speech-interface designer, accessibility specialist, QA lead, and cinematic interaction designer. Work directly in the existing repository. Inspect before changing. Preserve working behavior. Implement improvements in staged, reviewable increments rather than rewriting the app blindly.

The current project is a Vite + React 19 + TypeScript + Three.js application with MediaPipe HandLandmarker, browser SpeechRecognition, speech synthesis, NASA/ISS/EPIC/NeoWs/DONKI integrations, NASA media search, procedural Solar System and anatomy models, Apollo/Chandrayaan locations, offline fallback telemetry, a photoreal GLB hook at `/models/human/body.glb`, a 45/60 FPS renderer, and a hologram-pyramid mode. The most important existing files include `src/App.tsx`, `src/three/HologramCanvas.tsx`, `src/three/hologramModels.ts`, `src/three/humanBodyModel.ts`, `src/components/WebcamHandTracker.tsx`, `src/logic/gestureEngine.ts`, `src/logic/voiceCommands.ts`, `src/services/nasaDataService.ts`, and `TODO.md`.

Do not promise literal “100% perfect,” “100% real,” or medical-grade accuracy. Translate those wishes into measurable targets: source-backed values, explicit uncertainty, realistic but labeled visual abstractions, calibrated controls, reproducible tests, graceful degradation, and documented limitations. Never fabricate live telemetry, anatomy, citations, mission status, or model-training results. A generated visual must not be presented as a scan, photograph, clinical model, or direct observation unless it actually is one.

## Non-negotiable engineering rules

1. Start with a repository audit and an implementation plan. Do not delete existing functionality without evidence and a migration note.
2. Keep secrets out of client bundles, source control, logs, URLs, screenshots, and telemetry.
3. Treat live data as untrusted input: validate schema, timestamps, ranges, units, provenance, freshness, and partial failure.
4. Distinguish authoritative source data from interpolation, prediction, simulation, procedural art, and fallback values in both code and UI.
5. Use real astronomical algorithms and declared reference frames when claiming physical positions; do not scale distances and sizes together when that makes the scene unusable—offer a labeled exhibition scale.
6. Use anatomically reviewed assets or clearly labeled educational abstractions; do not call primitive placeholders textbook-accurate anatomy.
7. Speech-to-speech must have explicit consent, visible listening state, interruption, transcript controls, safe action confirmation, and a non-AI deterministic fallback.
8. Camera and microphone processing should be local by default, opt-in for network processing, and easy to stop.
9. Every interaction needs a reversible path, visible feedback, and an equivalent keyboard/pointer route.
10. Run typecheck, tests, production build, accessibility checks, and representative offline/live fixtures before delivery.

## Required delivery sequence

## Definition of done

The finished application must clearly label live, cached, simulated, and illustrative content; never silently invent a value; provide a source and timestamp for factual panels; recover from network, permission, model, WebGL, and speech failures; support hand, voice, keyboard, pointer, and visible UI control paths; prevent unintended destructive or privacy-sensitive actions; maintain stable frame pacing on declared device tiers; dispose resources cleanly; pass typecheck/tests/build; document known limitations; and preserve the existing `npm run dev`, `npm run lint`, `npm test`, and `npm run build` workflows.

Before claiming completion, produce: an architecture summary, data-source register, anatomy asset register, gesture/voice command matrix, speech-to-speech threat model, performance report, accessibility report, scientific-review checklist, test report, and a list of deferred work.
